## Решения по продукту и архитектуре

| № | Решение | Обоснование |
|---|---------|-------------|
| 1 | Один **модульный монолит**, не микросервисы | Проще развивать и деплоить; сервис выделяют при независимом релизе, команде, доступе или CI/CD |
| 2 | **Два уровня «проекта»**: бизнес-модуль = папка `modules/<name>`; пользовательский проект = запись в `platform.projects` | Пользовательский проект изолируется через `workspace_id`, отдельная БД/репозиторий на него не создаётся |
| 3 | `core` — только инфраструктура (config, db, logging, errors, security) | Не разрастается до «универсальной свалки» |
| 4 | Схема PostgreSQL — на бизнес-модуль (`platform` + отдельные схемы) | В одной БД, но разграничение владения таблицами |
| 5 | Миграции только добавляются, не переписываются | Alembic: новое изменение = новая ревизия |
| 6 | RBAC `user` / `admin`; авторизация отключена только в тестовом режиме | Определено ранее в диалоге |
| 7 | Секреты — файл окружения с правами `600`, в репозитории только `.env.example` | Проверка тока не по чату |

## Инцидент и уроки

`mv /mnt/d/opencodeai /mnt/d/opencodeai-legacy` вернул успех, но целевой каталог
оказался пустым — содержимое пропало из видимости WSL (сбой метаданных 9p/DrvFs).
Восстановлено 1:1 из снапшотов opencode (22 файла, сверка sha256 — совпадение).

**Правила на будущее:**
1. На `/mnt/d` (DrvFs) каталоги **не перемещать через `mv`** — только `mkdir`/`clone`
   или `cp` + проверка контрольных сумм + удаление источника.
2. Если WSL показывает `d?????????` — проблему решать со стороны Windows
   (`Remove-Item -LiteralPath 'D:\…' -Recurse -Force`), не командами WSL.
3. Git-репозиторий создавать **сразу** — история и снапшоты страховали бы ситуацию.

## Уточнение архитектуры (сессия восстановления контекста)

Саммари согласовано владельцем и записано в `docs/architecture/overview.md`.

| № | Решение | Как было до уточнения |
|---|---------|----------------------|
| 1 | Два уровня изоляции: **workspace → проекты** внутри него | спорило «проект = workspace» vs «workspace и проекты» |
| 2 | Справочник прав целиком в схеме `authorization` (`permissions`, `roles`, `role_permissions`, `role_assignments`) | предлагалось держать `permissions` в `platform` |
| 3 | `platform.module_grants` (доступ workspace × модуль) — в `platform` | — |
| 4 | `identity.users` — в схеме `identity`, `platform.user_settings` — конфигурация | — |
| 5 | REST: `/api/v1`, workspace в пути — `/api/v1/workspaces/{ws}/<module>/<resource>` | предложено на примере модуля `mail`, подтверждено |
| 6 | Типы API — OpenAPI-спека → генерация TS | открытый вопрос |
| 7 | Авторизация включается **после первого сквозного сценария**, не со старта | — |
| 8 | Обращение к таблицам — явные схемные имена, без `search_path` | старый bootstrap использовал `search_path` |
| 9 | Границы модулей — только конвенция, без автоматической проверки в CI | открытый вопрос |
| 10 | Назначение продукта — пока не определено, архитектуру не блокирует | — |
